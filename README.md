# tofu-setup

Run plain `tofu init / plan / apply` in GitHub Actions against an AWS account, while the
OpenTofu state and your variables live in a separate **state** account.

Add one step before your `tofu` commands. After it:

- `tofu init` uses the state bucket in the state account,
- the AWS provider deploys to the **target** account,
- every parameter stored under `/terraform/<env>/` in the state account is available as
  `var.<name>`.

Your OpenTofu code needs no backend block and knows nothing about the state account.

## Quick start

1. Create the two IAM roles. See [AWS setup](#aws-setup).
2. Store your variables as SSM parameters under `/terraform/<env>/` in the state account.
   See [Variables](#variables).
3. Add these to your repository's `.gitignore` (keep `.terraform.lock.hcl` committed):

   ```gitignore
   # generated by tofu-setup
   tfw_backend_override.tf
   # plan files hold variable values in plain text
   plan.bin
   # created by tofu init
   .terraform/
   ```

4. Add the action to your workflow:

   ```yaml
   permissions:
     id-token: write
     contents: read

   jobs:
     plan:
       runs-on: ubuntu-latest
       environment: production
       steps:
         - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
           with:
             persist-credentials: false
         - uses: opentofu/setup-opentofu@a1320f892987e89d278cc92dc5adc984fb93aca4 # v2.0.2
           with:
             tofu_version: "1.11.x"
             tofu_wrapper: false
         - uses: your-org/tofu-setup@<sha> # vX.Y.Z
           with:
             env: production
             state-account: "111111111111"
             target-account: "222222222222"
             state-bucket: my-state-bucket
             state-region: eu-south-1
         - run: tofu init
         - run: tofu plan
   ```

Ready-to-copy workflows: [`examples/plan.yml`](examples/plan.yml) plans on pull requests,
and [`examples/apply.yml`](examples/apply.yml) plans and applies on the main branch after
approval.

### Requirements

- The job needs `permissions: id-token: write`. Pull requests from forks get no OIDC
  token, so they can't use the action.
- The job must run in the GitHub environment the roles trust, e.g.
  `environment: production`. See [Trust policy](#trust-policy).
- OpenTofu must already be installed, for example by `opentofu/setup-opentofu`. This
  action does not install it. You need OpenTofu 1.10 or later, and 1.11 or later for
  ephemeral variables. `tofu_wrapper: false` keeps `tofu` output out of step outputs.
- `aws` (CLI v2) and `jq` must be on `PATH`. Both come preinstalled on GitHub-hosted
  runners.

## Your OpenTofu code

Write the root module as if it ran locally with a single account. Use no `backend` block,
an AWS provider with a region, and one `variable` block for each parameter:

```hcl
provider "aws" {
  region = "eu-south-1"
}

variable "db_password" {
  type      = string
  sensitive = true
  ephemeral = true # OpenTofu >= 1.11: kept out of state and plan files
}

variable "app_version" {
  type = string
}

variable "subnets" {
  type = list(string)
}
```

The action writes the backend configuration into `tfw_backend_override.tf`. OpenTofu gives
backend blocks in `_override.tf` files precedence over the module's own
([docs](https://opentofu.org/docs/language/files/override)). If someone adds a backend
block to the code later, the generated one still wins.

## Variables

Each parameter directly under `/terraform/<env>/` in the state account becomes the
variable with the same name:

| parameter | SSM type | in OpenTofu |
|---|---|---|
| `/terraform/production/db_password` | `SecureString` | `var.db_password`, masked in the logs |
| `/terraform/production/app_version` = `1.10` | `String` | `var.app_version` |
| `/terraform/production/subnets` = `subnet-a,subnet-b` | `StringList` | `var.subnets`, declare it as `list(string)` |

```bash
aws ssm put-parameter --name /terraform/production/app_version --type String --value 1.10
aws ssm put-parameter --name /terraform/production/subnets --type StringList --value subnet-a,subnet-b
aws ssm put-parameter --name /terraform/production/db_password --type SecureString --value "$DB_PASSWORD"
```

- **Values are used exactly as stored**, including a trailing newline. Watch out when you
  load a value from a file.
- **Types come from your `variable` blocks.** A `String` parameter `1.10` stays `"1.10"`
  for a `string` variable and becomes `1.1` for a `number`. For `list`, `map` and
  `object` variables, store the value as HCL or JSON, e.g. `{"a" = 1}`.
- **Names** may contain letters, digits and `_`, and must not start with a digit. Other
  parameters (e.g. `my-param`) are skipped with a log line. Deeper paths such as
  `/terraform/production/nested/x` are ignored.
- **Parameters without a `variable` block** produce a warning. With `strict-vars: true`
  they fail the step.
- **Values from tfvars files and `-var`** override the parameters.
- **Secrets** (`SecureString`) are masked line by line in the job log. Lines shorter than
  4 characters can't be masked, so avoid secrets that contain them. Declare secret
  variables `sensitive = true`, and preferably `ephemeral = true`.

## Inputs

| name | required | default | description |
|---|---|---|---|
| `env` | yes | | `dev`, `staging` or `production`. It is used in the defaults of `ssm-prefix`, `state-key` and `state-role-arn`. |
| `state-account` | yes | | 12-digit id of the state account. |
| `target-account` | yes | | 12-digit id of the account you deploy to. |
| `state-bucket` | yes | | S3 bucket holding the state. |
| `state-region` | yes | | Region of the state bucket and of the SSM parameters. |
| `state-key` | no | `<env>/terraform.tfstate` | State object key. Letters, digits, `/`, `=` and `` !-_.*'() `` only. |
| `state-role-arn` | no | `arn:aws:iam::<state-account>:role/terraform-<env>-action-role` | Role to use in the state account. Must belong to `state-account`. |
| `target-role-arn` | no | `arn:aws:iam::<target-account>:role/terraform` | Role to use in the target account. Must belong to `target-account`. |
| `target-region` | no | `state-region` | Default region for the AWS provider (`AWS_REGION`). |
| `ssm-prefix` | no | `/terraform/<env>` | Parameter path to read variables from. |
| `working-directory` | no | `.` | Directory of the root module, where you run `tofu`. |
| `strict-vars` | no | `false` | Fail when a parameter has no matching `variable` block. |
| `use-lockfile` | no | `true` | Lock the state with S3 native locking (OpenTofu ≥ 1.10). |
| `disable-input` | no | `true` | Set `TF_INPUT=0` and `TF_IN_AUTOMATION=1` for later steps. |
| `role-duration-seconds` | no | `3600` | Session duration for both roles. |
| `state-profile` | no | `tf-state` | Name of the AWS profile used for the state account. Change it only if it clashes with one you use. |
| `backend-file` | no | `tfw_backend_override.tf` | Name of the generated backend file. Must end in `_override.tf`. |

## Outputs

| name | description |
|---|---|
| `variable-names` | Space-separated names of the variables that were set (names only, never values). |
| `secret-count` | Number of `SecureString` parameters that were set. |
| `backend-file` | Absolute path of the generated backend file. |

## Plan and apply

Plan and apply in the same job, in the GitHub environment the roles trust. See
[`examples/apply.yml`](examples/apply.yml):

```yaml
jobs:
  apply:
    runs-on: ubuntu-latest
    environment: production
    steps:
      # checkout, OpenTofu and this action, as in the quick start
      - run: tofu init
      - run: tofu plan -out plan.bin
      - run: tofu apply plan.bin
```

- **Approval.** GitHub pauses the job until one of the environment's required reviewers
  approves it. Reviewers are set in the repository's **Settings → Environments →
  production → Required reviewers**, not in the workflow. Approval comes before the job
  starts, so reviewers approve running the job, not a specific plan.
- **No reviewers, no approval.** If the environment has no required reviewers, the job
  runs straight away. The same happens if the environment doesn't exist yet: GitHub
  creates it on first use, without protection rules. According to GitHub's docs, required
  reviewers on private repositories need GitHub Enterprise.
- **Don't upload `plan.bin`.** It contains the values of all non-ephemeral variables in
  plain text, even `sensitive` ones. In a single job it never leaves the runner.

## AWS setup

You need two roles, each trusted **directly** by GitHub's OIDC provider in its own
account. Don't add trust between the two roles.

| account | default role name | used for |
|---|---|---|
| state | `terraform-<env>-action-role` | state bucket and SSM parameters |
| target | `terraform` | everything your code manages |

To use different names, pass `state-role-arn` / `target-role-arn`.

### State role permissions

For `env: production`, with the bucket and parameters in `eu-south-1`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "StateObject",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": [
        "arn:aws:s3:::my-state-bucket/production/terraform.tfstate",
        "arn:aws:s3:::my-state-bucket/production/terraform.tfstate.tflock"
      ]
    },
    {
      "Sid": "StateBucket",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::my-state-bucket"
    },
    {
      "Sid": "Parameters",
      "Effect": "Allow",
      "Action": "ssm:GetParametersByPath",
      "Resource": [
        "arn:aws:ssm:eu-south-1:111111111111:parameter/terraform/production",
        "arn:aws:ssm:eu-south-1:111111111111:parameter/terraform/production/*"
      ]
    },
    {
      "Sid": "DecryptSecureStrings",
      "Effect": "Allow",
      "Action": "kms:Decrypt",
      "Resource": "arn:aws:kms:eu-south-1:111111111111:key/<key-id>",
      "Condition": { "StringEquals": { "kms:ViaService": "ssm.eu-south-1.amazonaws.com" } }
    },
    {
      "Sid": "Identity",
      "Effect": "Allow",
      "Action": "sts:GetCallerIdentity",
      "Resource": "*"
    }
  ]
}
```

- The `.tflock` object is only needed with `use-lockfile: true` (the default).
- `kms:Decrypt` is only needed when the `SecureString`s use a customer-managed key. Add
  the bucket's key as well if the bucket uses SSE-KMS.

### Target role permissions

Whatever your code manages, plus `sts:GetCallerIdentity`. It needs nothing in the state
account.

### Trust policy

Each role trusts GitHub's OIDC provider in its own account. A job that declares
`environment: <name>` gets the OIDC subject `repo:<org>/<repo>:environment:<name>`, on
pushes and pull requests alike. Trust that subject only:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::111111111111:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:your-org/your-repo:environment:production"
        }
      }
    }
  ]
}
```

Each state role belongs to one env, so it trusts that env's GitHub environment only.
The `terraform` role in a target account is shared by every env deployed there, so its
`sub` lists all of their environments, e.g.
`["repo:your-org/your-repo:environment:dev", "repo:your-org/your-repo:environment:staging"]`.

## Security notes

- **Later steps in the job can read the variables, secrets included.** This is the same
  exposure the deploy credentials already have. Keep the job down to checkout, OpenTofu
  setup, this action and `tofu` steps, and pin every action by commit SHA. If that is not
  acceptable for a workflow, use a wrapper that passes the variables to the `tofu`
  process only. This action can't do that.
- **Pull-request plans run the pull request's code with the production roles.** Approve
  them only after reviewing the change, including any change to the workflows.
- **On self-hosted runners, the state credentials remain in `~/.aws` after the job.**
  Use ephemeral runners or delete `~/.aws` at the end of the job.
- **Plan files contain variable values.** See [Plan and apply](#plan-and-apply).

## Troubleshooting

| message | what to do |
|---|---|
| `no OIDC token available; the job needs 'permissions: id-token: write'` | Add `id-token: write` to the job's `permissions`. |
| `Not authorized to perform sts:AssumeRoleWithWebIdentity` | Check that the role exists with the expected name, that the job declares `environment:`, and that the role's trust policy allows that environment. |
| `parameters with no matching variable block: …` | Declare the variables or delete the parameters. With `strict-vars: true` this fails the step. |
| `skipping /terraform/production/my-param: 'my-param' is not a valid variable name` | Rename the parameter using letters, digits and `_`. |
| `no parameters found under /terraform/production/` | Check `env`, `ssm-prefix` and `state-region`. |
| `No value for required variable` (from `tofu`) | There is no parameter for that variable under `/terraform/<env>/`, or its name was skipped. |
